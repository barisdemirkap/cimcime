## Findings

**What it is** (heretto.com): transforming complex information into clear, accessible content —
manuals, guides, FAQs, help files — prioritizing clarity and task-completion over any creative
or entertainment value.

**Five core principles** (heretto.com): clarity/precision (eliminate ambiguity, write with
purpose); audience-centered design (research the actual reader's technical background and real
goals before drafting, not just write generically); consistency (unified voice/terminology/
formatting builds trust and predictable navigation); logical organization (clear headings,
intuitive navigation, digestible chunks — information architecture, not just prose quality);
**documentation as product** — not an afterthought bolted on at the end, since quality docs
directly affect user experience, adoption, and satisfaction.

**Google's own program structure** (developers.google.com): two foundational courses pairing
pre-class self-study with instructor-led sessions, a standalone error-messaging course, and an
accessibility course offered either way. Audience explicitly includes software engineers and
product managers, not just dedicated technical writers. One sharp cross-cultural point: all
materials stay English-only because certain English writing recommendations become "culturally
or grammatically incorrect when translated" — a real localization caveat worth knowing before
assuming a style guide generalizes across languages.

**Direct relevance to this system — this very set of study files is an instance of the
discipline being researched**: the consistent structure every `docs/topics/*.md` file follows
(Sources → Findings → Practitioner notes, cited per claim) is "consistency" and "logical
organization" applied in practice, not just described abstractly. "Documentation as product, not
an afterthought" is the explicit reason `GLOSSARY.md`/`docs/adr/` exist as first-class, actively
maintained parts of this repo rather than optional notes nobody updates.
