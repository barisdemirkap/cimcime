## Findings

**What it actually is** (planyway.com — the sharper of the two sources): an executive report
answers exactly one question: "does this project require leadership's involvement or
reaction?" It's not a status report with the detail turned down — it's a different document
with a different job, built to let leadership weigh competing priorities across many things
they can't all track in depth themselves.

**Core components**: overall status summary with a health indicator, progress against
milestones, budget/resource status, key risks and blockers, **explicit decisions leadership
needs to make**, and what's changed since the last report. The last two are the parts a routine
status update usually lacks.

**Design principles**: RAG (red/amber/green) status indicators; consistent structure across
reporting cycles (so a reader can scan quickly because the shape is familiar); clean, not
decorative, design; data that's accurate and current, not stale.

**Named pitfalls**: mixing project status with product performance (different questions,
different audiences); marking everything "good" (defeats the entire purpose — the report exists
to surface what *isn't* fine); constantly redesigning the format (breaks the scannability
consistency buys); irrelevant detail; omitting inconvenient-but-important information (the
single most damaging failure mode, since it's the one that erodes trust once discovered).

**Indeed.com's complementary meeting-practice angle**: focus discussion on long-term strategy,
not daily operations; only discuss KPIs that reveal real performance, not vanity metrics;
allocate speaking time by relevance to actual goals; share the report *before* the meeting so
time isn't spent reading it live; assign responsibilities in writing, not verbally.

**The bottom-line insight, worth keeping verbatim** (planyway.com): effective executive
reporting requires *calibration over time* based on what leadership actually responds to — the
first version of a report format is a draft, not a template to lock in.

**Direct relevance to this system**: every end-of-ticket summary given to the user in this
session follows exactly this report's shape, not a status-report shape — status + what changed
+ risks/findings worth a decision (e.g. the Telegram/OpenClaw architecture finding, surfaced
explicitly rather than buried) + what's next. The pattern of asking "continue, or pause here?"
after each batch is itself the "does this require your involvement/reaction" question this topic
names as the defining feature of an executive report, not a status report.
